### 0.1 一个必须先讲清楚的硬约束（否则 v2.5 会白做）

你选的 **C-1 落盘缓存 + C-3 单机多进程** 组合，技术上是对的——但**只在三张卡同批交付时才对**：

```
❌ 错误做法：先加 4 个 worker，缓存各自独立
   → 同域被 4 个 worker 各解一次 → 4× 浏览器成本 + 4× 打站 + CF 侧风险↑
   → 吞吐数字变好看了，但每次求解依然 15s，稳态 QPS 没涨（重复劳动）

✅ 正确做法：共享落盘缓存 + 保活池 + 多 worker 同批上
   → 同域全局只解 1 次（缓存文件是唯一事实源），4 个 worker 只负责"导航"这一件事
   → "加进程 = 加冷路径吞吐" 才成立
```

因此 **T-08（FileStore+Fernet）、T-07（保活）、T-23（多进程池）构成不可拆分的原子交付单元**，验收项 E3 就是专门用来抓"假吞吐"的：如果 4 worker × 10 域 跑 10 分钟，总求解次数明显大于 `10 + 续期次数`，说明共享没生效，**这张卡不算完成**。

### 0.2 吞吐到底由谁决定（归因表，避免优化错对象）

| 路径 | 谁在处理 | 单次耗时 | 扩容手段 | 是否靠 worker 数量 |
|---|---|---|---|---|
| 热·Go 本地缓存命中 | Go 进程，**零 Python 参与** | 回放 1.3–1.6 s | Go 侧并发 + 连接池（T-04） | ❌ 无关 |
| 热·Go 未命中但 Solver 有 | Solver 读一个加密文件（~ms） | < 10 ms + 回放 | 无（已足够） | ❌ 无关 |
| **冷·需浏览器导航** | 浏览器 worker | 14–18 s | **多 worker 池（T-23）** | ✅ 强相关 |
| 续期·到期前重解 | 浏览器 worker | 14–18 s | 多 worker + 抖动错峰（T-07） | ✅ 强相关 |

**结论**：稳态 QPS 由 Go 回放能力决定；worker 池解决的是**冷启动与续期排队**。别把 4 个 worker 当成 QPS 提升 4 倍的依据——先把 T-04 的连接复用做对，热路径吞吐提升更直接。

## 4. 第一性原理与"吞吐优先"的张力处理

### 4.1 拆到不可再分

1. **求解的唯一产出是一串字节**（`cf_clearance=463 字节`）+ 一个 UA。浏览器存在的唯一理由，是"生成这串字节的那一刻，CF 相信它是真浏览器"。
2. **这串字节在有效期内与请求无关**——同域、同 IP、同 UA 的任何请求都能复用。它是**凭证**，不是**响应**。
3. 因此凭证应当被**持久化 + 预取 + 保活**，而不是在请求路径上现造。
4. 由 1–3：稳态 P99 应约等于回放延迟；稳态命中率应 ≥ 95%。
5. **失败主因不是性能，是失效**：四条硬边界（同 IP / 同 UA / ~30 min / 按域）任一被破坏 → 静默 403。所以必须补"边界被破坏时的自动重解与熔断"（T-10）。
6. **第二个第一性判断**：CF 校验的是"环境自洽"（IP 地理位置 ↔ 时区 ↔ 语言 ↔ 指纹 persona）。当前代码把 `geoip` 显式关掉（`solver/service.py:68`），等于主动放弃这一层——这是成功率上**最便宜**的一处改善（但必须 A/B 实测，不许拍脑袋开）。

### 4.2 张力：你选了"吞吐优先"，而第一性说"吞吐不是瓶颈"

**不回避**：按 §0.2 的归因，稳态 QPS 由 Go 回放决定，加 worker 不加稳态吞吐。**但你的选择在你的部署形态下是成立的**，理由如下：

- 多 worker 的真实价值不是"提高稳态 QPS"，而是**消除冷路径与续期路径的排队**。当前串行模型下，只要有一个冷域在解，**其它所有域的请求（哪怕只是来取已缓存的 clearance）也会排在它后面**——这是串行 worker 的结构性缺陷，请求越快、域越多，伤害越大。
- 配共享落盘缓存后，"取已缓存 clearance"变成"读文件（~ms）"，**不再占用 worker**；worker 只处理"必须导航"的任务。这才是池化的意义。
- 所以把目标定为：**冷路径吞吐 ≥ N×(1/18s)**（可加进程线性扩）+ **热路径完全不碰 worker**。稳态 QPS 另由 T-04 承担。

**因此本指南的吞吐目标分两类，不许混谈**：

| 类别 | 指标 | 手段 |
|---|---|---|
| 冷/续期吞吐 | 4 worker 时 ≥ 3× 单 worker | T-23 + T-08 |
| 稳态回放吞吐 | 单 Go 进程 ≥ 50 QPS（待实测） | T-04（连接池/HTTP2）+ T-09 |

## 5. 根因级问题清单

> 格式：**现象 → 证据 → 根因 → 影响 → 修法**。P0 = 上线阻塞，P1 = 主流程高概率故障，P2 = 体验/维护，P3 = 增强。

### P0-1｜求解服务无任何鉴权，且文档建议对外暴露 【CRITICAL】

- **证据**：`solver/service.py:210-246` 的 `do_GET`/`do_POST` 无任何 header 校验；全文无 `Authorization`/token 逻辑（已验证 grep 无命中）。`docs/最终方案与实现结果.md:121` 的部署命令是 `--host 0.0.0.0 --port 8878`——**文档主动建议暴露到公网**。
- **根因**：把研究脚本直接升格为服务，服务化四要素（鉴权/限流/预算/可观测）做了 0 个。
- **影响**：凭证泄露 + 资源滥用（单 worker 被一次恶意请求占住 15–300 s 即永久不可用）。**在你要上 4 worker 之后，滥用面放大 4 倍。**
- **修法**：**T-01**（自动生成 token 写 `.env`）+ **T-03**（inflight 上限）。

### P0-2｜输入校验不足：SSRF + 超时/force 无上限 【CRITICAL】

- **证据**：`solver/service.py:232-239`（只校验 `http(s)` 前缀与长度）；`:233` `timeout = float(...)` 无 clamp；`:234` `force = bool(...)` 无节流。
- **影响**：
  1. **SSRF**：可让浏览器导航到 `127.0.0.1:*`、`169.254.169.254/latest/meta-data/`、内网地址；虽不返回 body，但**返回 `title`**（`:117`、`:152`），足以做内网存活探测与标题泄露。
  2. **worker 独占 DoS**：`timeout=1e9` 让单 worker 卡满 `_submit` 的 300 s（`:92`），队列雪崩。
  3. **缓存穿透**：`force=true` 无限重解 = 免费送算力。
- **修法**：**T-02**。

### P0-3｜并发与队列无治理：无界队列 + 无 inflight 上限 【CRITICAL】

- **证据**：`solver/service.py:62`（`queue.Queue()` 无界）、`:88-96`（`_submit` 等 300 s）、`:260`（`ThreadingHTTPServer`）。
- **根因**：单 worker 串行模型没有配套**准入控制**。串行本身是对的（Playwright sync 绑线程，见 `docs/最终方案与实现结果.md:135-143`），但缺闸门。
- **影响**：并发 > 10 时后到请求排队 300 s 后统一超时；HTTP 线程数随并发线性增长；客户端已放弃的请求仍在队列里烧浏览器。
- **修法**：**T-03**。

### P0-4｜超时预算被放大 2 倍，与客户端不匹配 【HIGH】

- **证据**：`solver/service.py:103`（`goto(timeout=int(timeout*1000))`）与 `:104`（`deadline = time.time() + timeout`）——**deadline 在 goto 之后才起算**。
- **影响**：Go 侧传 `timeout=60`（`gocfsolve/cfsolve.go:92`）、`http.Client Timeout=120s`（`:89`）→ 服务端可跑到 120 s；example 的 ctx 180 s（`examples/endtoend/main.go:26`）刚好掩盖了它。
- **修法**：**T-06**。

### P0-5｜Go 回放绕过自身 HTTP 客户端配置，可无限 hang 【HIGH】

- **证据**：`gocfsolve/cfsolve.go:197`（`return http.DefaultClient.Do(...)`），绕过 `c.hc`（`:89`）的 Timeout 与任何 Transport 配置。
- **影响**：回放**没有超时保护**（只靠调用方 ctx）；`DefaultTransport` 的 `MaxIdleConnsPerHost=2` 导致反复 TLS 握手——这是"稳态回放吞吐 ≤ 50 QPS"目标的**直接阻塞项**。
- **修法**：**T-04**。

### P1-1｜并发缓存未命中会打穿求解服务（thundering herd）

- **证据**：`gocfsolve/cfsolve.go:103-115`——`Get` 只在 `mu` 内读缓存，随即释放锁做网络求解；无 per-host 单飞。
- **影响**：N 个并发请求打到冷域 → N 次 `/solve`；单 worker 串行会把这些请求排成一队。**上多 worker 后情况缓解，但客户端仍会制造 N 倍无效请求。**
- **修法**：**T-09**。

### P1-2｜回放失败不会自愈：403/挑战页原样返回

- **证据**：`gocfsolve/cfsolve.go:175-198`，`Do`/`DoWith` 不检查状态码与 `cf-mitigated`，不失效缓存、不重解。
- **影响**：cookie 因 IP/UA/TTL 漂移失效后，业务侧稳定拿到 403 直到缓存自然过期（最长 25 min）。**这是最可能在生产里真实咬人的缺陷。**
- **修法**：**T-10**。

### P1-3｜cookie 被压成 name→value，丢失 domain/path/expires

- **证据**：`solver/service.py:107`（`{c["name"]: c["value"] for c in ctx.cookies()}`）；`gocfsolve/cfsolve.go:46-57`（无差别拼头，**map 迭代顺序还不确定**）。
- **影响**：①多域/子域场景会把不匹配域的 cookie 一起发出去，请求头异常可能被判异常指纹；②`expires_at` 是**拍的**（`solver/service.py:159` `time.time() + self.ttl`）；③`cf_clearance` 不在头首位。
- **修法**：**T-11** + **T-12**。

### P1-4｜硬编码绝对路径，README 声称的环境变量其实没接上 【文档-实现不一致】

- **证据**：
  - `go-jseng/main.go:11` `const dir = "D:\apk-analysis\cf-jsd-recon\"`，只读 `CF_OPT_PATH`；而 `README.md:215-217` 写的是 `CF_SCRIPT_PATH=... go run go-jseng/main.go` → **脚本路径根本没被读取**。
  - `go-replay/main.go:25` `dir := "D:\apk-analysis\cf-jsd-recon\gotest\"`；`README.md:220` 写的 `CF_COOKIE_DIR` → **代码里不存在该变量**。
- **根因**：上一轮"脱敏"只改了一半（历史记录声称 4 个环境变量，实际落地 2 个）。

## 7. 方案对比与选型（含已拍板项）

> 已拍板的（§0）标 **✅已定**，不再论证；其余仍给对比供执行者复核。评分 1–5（5 最优）。

### D1 如何把求解移出请求路径？ ✅已定 = 后台保活（a）

| 方案 | 可行性 | 成本 | 维护 | 性能 | 扩展 | 风险 | 合计 |
|---|---|---|---|---|---|---|---|
| **D1-a 后台保活 + 预续期（采用）** | 5 | 4 | 4 | **5** | 4 | 4 | **26** |
| D1-b 请求触发 + 异步回填 | 5 | 4 | 4 | 3 | 4 | 4 | 24 |
| D1-c 外部 cron 调 `/solve?force=1` | 5 | 3 | 3 | 4 | 5 | 3 | 23 |
| D1-d 纯客户端侧保活（Go goroutine） | 4 | 3 | 3 | 4 | 4 | 3 | 21 |

**为何 a**：服务端才知道"到期时间 / 上次成败 / 退避状态"，保活信息最全；对外仍是纯 HTTP 契约。**取舍**：服务变成有状态调度器，因此必须配 T-08 的共享文件缓存，否则多 worker 各保活一遍。

### D2 共享缓存技术选型 ✅已定 = 落盘文件 + Fernet（b）

| 方案 | 可行性 | 成本 | 维护 | 安全 | 跨进程 | 结论 |
|---|---|---|---|---|---|---|
| D2-a 仅内存抽象 | 5 | 5 | 5 | 5 | ❌ | 不满足 C-3 多进程共享 |
| **D2-b 落盘 + Fernet 加密（采用）** | 4 | 3 | 4 | 4 | ✅ | 跨进程天然共享、重启不丢、无外部服务 |
| D2-c Redis | 4 | 3 | 3 | 3 | ✅ | 多一个外部依赖与网络跳；v3 若跨机再考虑 |

**D2-b 的强制设计要求**（写错就等于没加密，或会互相打架）：

1. **一个域一个文件**，文件名 = `sha256(host)[:16].hex` → **磁盘上不出现域名**（减少元数据泄露）。
2. **写入必须原子**：同目录写 `*.tmp` → `os.replace()`。**禁止加文件锁**（`flock` 在 Windows 语义差、在 NFS 不可靠）。读方容忍"文件不存在 / 半截 / 解密失败"→ 一律视为未命中并删除该文件。
3. **跨卷会失败**：`os.replace` 跨设备抛 `OSError(EXDEV)` → 启动时校验 `--cache-dir` 与 `tmp` 同卷。
4. **密钥派生**：`salt.bin`（16B，`os.urandom`，0600，原子写）→ `PBKDF2-HMAC-SHA256(token, salt, 200_000, 32)` → `base64.urlsafe_b64encode` → Fernet key。**启动时算一次缓存进内存**，不许每请求算。
5. **换 token = 自动作废全部缓存**（密钥变 → 解密失败 → 视为未命中并覆盖）。这是特性不是 bug，写进文档。
6. **文件数上限**（默认 4096）+ 启动清扫 + 每 60 s purge 过期项；过期即删（不在磁盘留死凭证）。
7. **权限**：目录 `0700`、文件 `0600`；Windows 用 `subprocess` 调 `icacls <path> /inheritance:r /grant:r "%USERNAME%:F"`（不引 `pywin32`）。icacls 失败只告警不阻塞，但要在启动日志里明确记录。
8. **不落明文**：加密后的 blob 里才有 cookie 值；`strings` 搜 `cf_clearance=` 必须无命中（B5 验收）。

### D3 Go 侧并发去重 ✅已定 = 零依赖 per-host inflight

| 方案 | 成本 | 新增依赖 | 结论 |
|---|---|---|---|
| **D3-a per-host inflight map（采用）** | 4 | 0 | 约 40 行，可单测 |
| D3-b `golang.org/x/sync/singleflight` | 5 | +1 | 可行但非必要 |
| D3-c 全局串行 | 5 | 0 | 跨域互相阻塞 |

### D4 鉴权方式 ✅已定 = 静态 Bearer + 首次自动生成写 `.env`（c）

| 方案 | 安全 | 运维 | 结论 |
|---|---|---|---|
| D4-a 静态 Bearer，env 读取 | 4 | 5 | 需要人配 |
| **D4-c 自动生成写 `.env`（采用）** | 4 | **5** | 零配置且默认安全；需处理权限与并发首启竞态 |
| D4-b mTLS | 5 | 2 | 过度 |

**自动生成的强制细节**（T-01 会展开）：

- 读取顺序：`CF_SOLVE_TOKEN` env → `--token-file`（默认 `./.env`）→ **都无则生成** `secrets.token_urlsafe(32)` 并**原子写**（`O_CREAT|O_EXCL`，失败则重读，解决多进程首启竞态）。
- 日志只打 `token_fingerprint=sha256(token)[:8]`，**永不打 token 本体**。
- `.env` 必须进 `.gitignore`，且**不许**在 Dockerfile 构建阶段触发服务启动（否则 token 会烤进镜像层）。
- 多 worker 共享同一 `.env` → 全部读到同一 token → 客户端一个 token 通吃。

### D5 挑战检测判据 ✅已定 = 状态码/响应头为主 + body 前缀抽样

- 主判据：`status ∈ {403,503}` 或响应头含 `cf-mitigated`（零成本）。
- 次判据：仅当 `200` 且 `Content-Type: text/html` 时读**前 8 KB** 检查 `Just a moment` / `__cf_chl` / `cf-browser-verification`；命中则**必须还原 body**：`resp.Body = io.NopCloser(io.MultiReader(bytes.NewReader(prefix), resp.Body))`。这是最容易写错的一处，T-10 有专门单测。

### D6 并发模型 ✅已定 = 单机多进程 + 共享目录（a）

| 方案 | 吞吐 | 增量内存 | 改动面 | 风险 | 结论 |
|---|---|---|---|---|---|
| **D6-a 多进程 worker 池 + 共享缓存目录（采用）** | N× 冷路径 | N×700 MB | 中（新增 pool/调度，不动求解核心） | 中 | 与"单线程持浏览器"的既有结论完全兼容 |
| D6-b 单进程 async 多 context | ~N× | 小 | 大（核心从 sync 改 async） | 高 | **明确不做**（重构，违背约束） |
| D6-c 纯横向扩（多机多实例） | N× | N×700 MB | 0 | 低 | v3 跨机时用，本次单机 |

**D6-a 的强制设计**：

1. **进程托管不做在 Python 里**（复杂度跳变）。用 `run.ps1`/`docker-compose` 起 N 个 `service.py --port 8878+i --cache-dir <同一目录>`。
2. **派发在 Go 客户端做**：`host → 一致性哈希 → 端口`；但**必须先查本地缓存**，命中则不经任何节点。非 Go 客户端用可选的 `solver/pool.py`（薄代理，仅转发）。
3. **摘除/回归**：Go 侧每 10 s 打各节点 `/health`，连续 2 次失败即摘除；恢复后自动回归。**因此 `/health` 必须能反映浏览器死活**（依赖 T-15）。
4. **双保险**：一致性哈希 + 共享缓存。即使哈希抖动，同域也不会被解第二次（E3 验收）。

### D7 实验卫生（因 V-1 决策新增） ✅已定 = 50 请求、分两批、有停止条件

见 §20。要点：批次 A（3 站 × 3 次 = 9 次）作为可行性闸门，通过才放批次 B（7 站 × 5 次 = 35 次），预留 6 次给手工排查；同站串行、间隔 ≥ 30 s；累计 ≥ 5 次失败立即停止并报告"IP 可能被提分"。

## 12. 性能专项

### 12.1 目标（**待实测，非承诺**）

| 指标 | 基线 | 目标 | 手段 |
|---|---|---|---|
| 冷路径吞吐（4 worker） | 1/18s ≈ 0.056 QPS | **≥ 3×**（约 0.17 QPS） | T-23 + T-08 |
| 稳态回放吞吐（Go） | 未测 | **≥ 50 QPS** | T-04 连接池/HTTP2 + T-09 |
| 热路径端到端 P99 | 未测（P50≈1.5s） | **≤ 2.0 s** | T-07 消除同步求解 |
| 稳态命中率 | 未测 | **≥ 95 %** | T-07 + T-12 |
| 冷求解耗时 | 18.1 s | ≤ 基线 + 10 % | T-13（**不许为提速牺牲成功率**） |
| 单次求解最坏耗时 | 120 s（2×） | **≤ 60 s** | T-06 |
| 并发 50 挂死率 | ≈100 % | **0 %** | T-03 |
| 4 worker 内存 | N×700 MB | **≤ 3.5 GB** | 测量 + 必要时降到 3 worker |

### 12.2 测量方法（先有测量再谈优化）

1. **Go**：`net/http/httptrace` 打点（DNS/connect/TLS/首字节）输出分位；或 `curl -w` 对照。
2. **Python**：`time.monotonic()` 分段落结构化日志 `phase`：`goto` / `wait_cookie` / `close_ctx` / `cache_read` / `cache_write`。
3. **压测脚本** `scripts/loadtest.py`：
   - `--hot`：打本机 fake 服务，测 Go 回放吞吐（E2）
   - `--cold`：N 个不同域并发各解 1 次（E1）
   - `--share`：4 worker × M 域 × 10 min，统计 `solves` 总数（E3）
   - 输出 p50/p90/p99、错误分类、inflight 峰值、内存曲线
4. **内存**：`psutil` 采样，记录"空闲 / 1 context / 4 worker 并发"三档。

### 12.3 明确**不做**的优化（避免踩坑）

- ❌ 把 sync API 改 async 重写核心（D6-b）：违背"不重构"，风险远大于收益。
- ❌ 为提速降低 `wait_until` 到 `commit` 或缩短 budget：牺牲成功率。
- ❌ 用 `page.content()` 做成功判据（大页面序列化很贵，`ctx.cookies()` 足够）。
- ❌ 无证据地调大 `ttl`：到期由 CF 决定，调大只会返回死 cookie。
- ❌ **为了 E1 好看而关掉共享缓存**：那测的是"重复劳动吞吐"，无意义且会抬高 CF 侧风险。
- ❌ 在每个请求里做一次 PBKDF2（200k 次迭代）：密钥必须在启动时派生一次并缓存。

## 14. 可观测性与运维

- **指标**：见 T-15。多进程按 §14 的聚合方案（推荐 Prometheus 多 target）。
- **看板三块**：①求解成功率与耗时分布（按 worker 分）；②缓存命中率与域数量；③inflight/队列深度与 429 计数。
- **告警阈值（建议，按实际调）**：
  - 5 min 求解成功率 < 70 % → P1
  - 单域连续失败 ≥ 3 → 域级（该域风控可能变了）
  - `queue_depth > 16` 持续 1 min → 扩容信号
  - `browser_alive == 0` → P0
  - **`cache_hits/(hits+solves)` 骤降 → 优先查"共享缓存是否还在共享"**（多 worker 后最常见的运维事故）
- **运维手册** `docs/运维手册.md`：起停、扩缩（加 worker）、常见故障三步定位（浏览器崩溃 / clearance 全失效 / CF 改版 / 缓存目录权限被改）。

| `.env` 被误提交 / 被镜像烤进去 | 中 | 高（凭证泄露） | `.gitignore` + 构建期不启动服务 + 提交前 `grep` |
| 4 worker 内存超预算（>3.5 GB） | 中 | 中 | 降到 3 worker；或 `geoip=False`（省内存）；E4 实测决定 |
| worker 崩溃后请求打到死节点 | 中 | 中 | `/health` 必须反映浏览器死活（T-15）；摘除 ≤20 s（E5） |
| **10 站 × 50 次被打站 IP 提分** | **中高** | 中（污染后续实验） | §20 分批 + 停止条件 + 串行 ≥30 s；批次 A 失败即停 |
| SSRF 校验误伤（国内站解析到 CDN 私网段） | 中 | 中 | `CF_SOLVE_HOST_ALLOWLIST`；错误信息说明原因 |
| 预热把失败域反复打 | 中 | 中 | 指数退避 + 1 h 封顶（T-07） |
| 真实 TTL 比预期短（session cookie）→ 命中率不升 | 中 | 中 | 先测 3 站真实 `expires` 再定兜底 TTL |
| `DoWith` 读 body 前缀未还原 → 业务拿到残缺页面 | 中 | 高（静默错数据） | T-10 专门单测 #11 |
| geoip 开启反而降成功率 | 中 | 中 | T-14 严格 A/B，无收益就默认关并记录 |
| 升级 camoufox 导致指纹变化、成功率归零 | 中 | 高 | 版本锁 + 发版前跑 A4 |
| 执行者顺手重构 | 中 | 高 | 本指南"禁区"条款 + 逐卡 diff 审查 |

**回滚原则**：每张卡都能在不改其它卡的前提下单独回滚；冲突时优先回滚，不叠补丁。

**停止并报告阻塞的条件**：
1. 需要真实付费 API / 未授权目标；
2. §20 预算内累计失败 ≥5 次（IP 可能被提分）→ 停止，不要继续烧；
3. camoufox 在某站稳定失败且 A/B 已排除配置问题（研究结论变更，需你决策换路线）；
4. 某 P0 修复要求重构（先出影响分析，等确认）；

## 20. 实验卫生规范（因 V-1 决策新增，**强制执行**）

### 20.1 预算分配（总计 50 次真实过盾请求）

| 批次 | 站点 | 次数 | 目的 | 闸门 |

> 前 6 个站来自历史采样里**已确认触发 managed challenge** 的站点（`docs/Cloudflare过盾方案可行性侦察报告.md` §2.4）；后 4 个为同批采样中的候选。

### 20.2 硬性规则

1. **只发 GET 首页**，不登入、不提交表单、不翻页、不并发打同一站。
2. **同站串行，间隔 ≥ 30 s**（避免触发速率风控，也让结论可归因）。
3. 每站先做 1 次「无 cookie 基线」记录 `status` + `cf-mitigated`，再开始求解实验。
4. **累计失败 ≥ 5 次（403 或未拿到 clearance）→ 立即停止全部实验**，写下"IP 可能已被提分"结论，等 24 h 后再评估。**不许换 IP 立刻重试**（会掩盖结论、也违背"不绕过授权边界"）。
5. 每次请求记录：`站` / `时间` / `status` / `是否拿到 clearance` / `耗时` / `cType`（若有）。落 `plans/证据/exp-<日期>-<批次>.log`，**脱敏**（clearance 值写 `<redacted>` 或只写长度）。
6. 实验脚本必须支持 `--dry-run`（只打印将要打的 URL 序列），**先用 dry-run 核对预算再真跑**。
7. **CI 里永不执行**这些实验（CI 只跑 mock）。

## 附录 B：指标口径定义

| 指标 | 定义 |
|---|---|
| 冷求解 | 缓存无该域或已过期，且本次触发了浏览器导航 |
| 缓存命中 | 请求路径上**未**触发浏览器导航（含 Go 本地命中与 Solver 文件缓存命中） |
| 命中率 | `cache_hits / (cache_hits + cold_solves)`，30 min 滑动窗 |
| 端到端延迟 | 客户端发起 `Get` 到拿到可回放 `Clearance` 的墙钟时间 |
| 求解成功率 | `solve_total{result="ok"} / solve_total`（分母含超时与无 cookie） |
| 双向失败 | 求解成功但回放仍拿到挑战页（**必须单独计数**，最危险的静默失败） |
| 冷路径吞吐 | 单位时间内完成的"必须导航"求解次数（N 个不同域并发） |
| 稳态回放吞吐 | 单位时间内完成的热路径回放请求数（Go 本地缓存命中） |

## 附录 C：术语

| 术语 | 含义 |
|---|---|
| clearance | 本文特指 `cf_clearance` cookie，按 域+IP+UA 绑定的过盾凭证 |
| 硬边界 | 同出口 IP / 同 UA / ~30 min 时效 / 按域隔离，违反任一即失效 |
| 单飞（singleflight） | 并发同 key 请求合并为一次真实调用 |
| 熔断 | 连续失败达阈值后暂时不再尝试，直接快速失败 |
| 预热 / 保活 | 后台提前求解或续期，使业务请求不落入冷路径 |
| 原子交付单元 | 必须一起上线的多张卡（如 T-07+T-08+T-23），拆开会产生假成果 |
| 假吞吐 | 进程数变多但同域被重复求解，指标好看、实际能力没涨（E3 专治） |
