## 0. 本版速览（先读这一页）

**一句话结论**：这个仓库已经是一个"带鉴权、有 174 项测试、多后端可切换、可多进程扩容"的可部署服务；
但它有 **两条断掉的价值链** 和 **两个被绕过的治理层**，三者叠加使得"纯协议优先"这条被文档大力推荐的路线，
一旦按文档启用，会同时让缓存全失效、SSRF 守卫失效、metrics 全变 0。

### 0.1 三处真洞（一句话版）

| # | 洞 | 后果 | 等级 |
|---|---|---|---|
| 1 | **`/detect` 与 `/solve` 是两个互不连通的入口** | 无盾站也要付 16–20s 的浏览器求解；纯协议站也没被优先选中。探测能力已具备，却没人用它做决策 | P1（价值损失，不致命） |
| 2 | **配任一额外后端后，`/solve` 的 SSRF 守卫被整体绕过**（本轮已实测复现） | 已认证调用方可让服务器去打内网/元数据地址；且纯协议后端无缓存、无准入、metrics 全 0 | **P0（安全 + 治理）** |
| 3 | **Go 回放层遇到 403 / 挑战页原样透传**（v3.0 的 T-10，仍未做） | `cf_clearance` 一失效，业务侧稳定吃 403 直到缓存自然过期——会被当"服务挂了"上报 | **P0（生产咬人）** |

## 3. 第一性原理：价值链上到底哪一环在漏水

把系统拆到不能再拆，只有一条价值流：

```
业务请求 ──→ ①判定"对面有没有盾/什么盾"（现在：没接）
                │
                ├─无盾───────────→ ②直连取数          （现在：也走浏览器，白等 16-20s）
                ├─有盾·CF────────→ ③取凭证 → ④回放 → 200
                └─有盾·其他──────→ 明确告知"不支持"     （现在：也盲目求解，白等 16-20s）

③取凭证：候选后端 = 纯协议(18s, 零浏览器) / Camoufox(16-20s, 1.2GB) / pydoll(60-88s) / FlareSolverr
                └─ 现在：**固定顺序盲试，且不共享预算，不共享缓存，不共享准入**

④回放：1.3s，Go 侧
                └─ 现在：**凭证失效时原样透传 403**
```

四段里有三段是**信息已在手、决策没发生**：

1. **①→②③ 的判定没接上**：`/detect` 已经能算出 `route ∈ {direct, direct_unless_blocked, browser, pure_protocol_may_work, browser_token, browser_cookie, unsupported_or_browser}`
   （`solver/detect.py`，实测真机 3 站分类正确），但这个结论**从不进入求解决策**。调用方要自己调两次、自己写 if。
   → 这是"能力已建、闭环未合"，成本最低、收益最大的一刀（**§7**）。
2. **③ 的候选之间没有统一治理**：`BackendRouter` 把整条链串起来后，**只有落到 Camoufox 的那一棒才享受 `Solver` 的缓存/准入/指标/守卫**；
   纯协议与 pydoll 这两棒是"裸奔"的（§4-P0-1、P1-1）。治理被绑在实现上，而不是绑在入口上 —— 这是结构错位。
3. **④ 的失败被静默**：唯一还在请求路径上等着咬人的缺陷（T-10）。

**所以 v4.0 的排序只能是**：先把②③④的治理缝死（W1），再把①的判定接进③（W2），
然后才谈缓存形态与指标体系（W3）——因为缓存/指标都要依赖"治理绑在入口"这个前提，否则做出来又只覆盖一半路径。
最后工程化（W4），因为它决定"这些改动敢不敢合"。

**仍然不做**：把 detect 做成独立微服务、做前端控制台、做多租户计费——当前需求强度（稳态 ≈0.08 QPS）撑不起这些复杂度。

> 格式：**现象 → 证据 → 根因 → 影响 → 修法**。等级：P0=上线阻塞 / P1=主流程高概率故障 / P2=体验与维护 / P3=长期。

### P0-1｜配了任一额外后端后，`/solve` 的 SSRF 守卫被整体绕过 【P0 · 安全 · 已验证】

- **现象**：`POST /solve {"url":"http://127.0.0.1:8903/health"}` 在 `--cfsolve-bin` 配置生效时，
  请求被派发给纯协议后端，二进制实际收到 `--page http://127.0.0.1:8903/health`。
- **证据（实测，本轮）**：
  ```
  $ python solver/service.py --port 8903 --no-auth --cfsolve-bin <abs>/fake_cfsolve.exe --cfsolve-profile .tmp-probe/fake_profile.json
  $ curl -s -X POST http://127.0.0.1:8903/solve -d '{"url":"http://127.0.0.1:8903/health"}'
  → attempts: [{"backend":"cfsolve","ok":false,"error_code":"unsolved","stage":"wait"},
                {"backend":"camoufox","ok":false,"error_code":"invalid-request","stage":"validate"}]
  $ cat .tmp-probe/argv.txt
  → [--page http://127.0.0.1:8903/health  <tmpdir>/run --solve --fingerprint .tmp-probe/fake_profile.json]
  ```
- **证据（静态）**：SSRF 守卫 `_check_target` 全仓只有两个调用点——`solver/service.py:1006`（`Solver.solve` 内）
  与 `:1484`（`/detect` 内）。而 handler 在配了 router 时**根本不进 `Solver.solve`**：
  ```python
  # solver/service.py:1431-1443
  if self.router is not None:
      result = self.router.solve(url, timeout=..., force=..., want=..., sitekey=..., ...)   # ← 无 _check_target
  else:
      result = self.solver.solve(...)                                                        # ← 有守卫
  ```
  最终 4xx 是**第二个后端（camoufox）**抛的，属于"碰巧兜住了"，不是设计保证。
- **根因**：治理（守卫/准入/缓存/指标）被实现成 `Solver` 的方法，而不是**入口层（handler）的职责**。
  一旦走 router 就把整个 `Solver` 绕过去了。`backends.py:236` 的注释显示作者意识到"落到 fallback 就等于把
  SSRF 守卫、鉴权、背压全部绕过"，但只堵了 fallback 的**终止码**，没堵**主路径**。
- **影响**：已认证调用方（token 泄漏或内部误用）可让服务器访问内网/云元数据地址。
  纯协议后端是**子进程直连**（`subprocess.run`），pydoll 是**自开 Chrome 直连**，两者都不经过浏览器的 route 拦截器
  （`_install_request_guard` 只装在 Camoufox 的 context 上，`:813-940`）。
- **修法**：**T-28**——把守卫/准入/指标上提到 handler 入口，所有后端共用（详见 §6 与 §10）。

### P0-2｜Go 回放遇 403 / 挑战页原样透传（T-10，v3.0 遗留） 【P0 · 生产咬人 · 静态确认】

- **证据**：`gocfsolve/cfsolve.go:381-412` `DoWith` 组装请求后直接 `c.replay.Do(req)` 返回，
  **无状态码检查、无 `cf-mitigated` 头识别、无缓存失效、无重解**。
- **加重项（本轮新发现）**：`solver/service.py:645` 的 `cache_key` docstring 写着
  「UA 若真变了、且站点也校验，客户端回放会拿到 403 —— **由既有自愈逻辑重解，不会静默**」。
  **这条自愈逻辑不存在**。文档级的"我们已经处理了"是比缺陷本身更危险的信号：后续会话读到这里会跳过它。
- **影响**：cookie 因出口漂移/TTL/CF 侧提前作废而失效时，业务侧稳定 403 直到缓存自然过期（最长 `--ttl` 1500s）。
- **修法**：**T-10**（§6）。

### P1-1｜纯协议 / pydoll / 兜底后端"三不沾"：不缓存、不准入、不进指标 【P1 · 已验证+静态确认】

- **证据**：
  - 不缓存：`CfsolveBackend.solve` / `PydollBackend.solve` 只 `return dict`，从不触碰 `self._store`（`cfsolve_backend.py:143-183`、`pydoll_backend.py:187-203`）。
  - 不准入：`_inflight` 信号量只在 `Solver.solve:1043` 获取；router 路径没有对应物 ⇒ 并发 N 个请求 = N 个 `subprocess`/N 个 Chrome。
  - 不进指标：`_solves/_hits/_failures` 只在 `Solver.solve` 里累加；router 路径全 0。**实测 V12：一次真实后端尝试后 `/health` 仍 `solves=0, failures=0`**。
- **影响**：按 README / `docs/纯协议-cfsolve.md` 的推荐启用纯协议后，热路径命中率归零（每次都重跑 18s 子进程），
  且能被打穿（无准入）。而 `/metrics` 会说"一切正常"——**观测数据在撒谎比没有数据更坏**。
- **修法**：**T-29**（后端治理收口）。

### P1-2｜`cfsolve` / `pydoll` 返回 `expires_at=0` ⇒ 三层缓存全部失效、客户端每次都重解 【P1 · 已静态确认】

- **证据**：
  - `solver/cfsolve_backend.py:152` → `"expires_in": 0, "expires_at": 0.0`
  - `solver/pydoll_backend.py:196-197` → 同
  - `gocfsolve/cfsolve.go:57-62` `expiresAt()`：`ExpiresAt>0` 才用它，否则 `now + ExpiresIn` ⇒ `now+0 = now`
  - `cfsolve.go:288` `Get`：命中条件是 `time.Now().Add(c.renewBefore).Before(cached.expiresAt())` ⇒ 对 `now` 恒为 false ⇒ **必走求解**
- **这是回归，不是新问题**：仓库**自己**为 FlareSolverr 立过这条不变量并写了理由——
  `tests/test_backends.py:296-300`：
  ```python
  assert out["expires_in"] > 0 and out["expires_at"] > 0, \
      "expires_at=0 会让 Go 侧立刻判过期，导致每次回放都重新求解"
  ```
  后来新增的两个后端**没有继承这条约束，也没有对应测试**；`tests/test_strategies.py:117` 只断言 `cacheable is True`，
  **没断言 `expires_at > 0`** —— 测试在为这个 bug 背书。
- **影响**：违反 `docs/对接-new-api.md` 承诺的"热路径 <100ms"，直接打穿 SLO A3。
- **修法**：**T-30**——为两个后端补真实 TTL（cfsolve 无 cookie expires 时按 `DEFAULT_TTL` 保守取；
  pydoll 从 CDP `Network.getCookies` 的 `expires` 取），并把 `expires_at>0` 提升为**所有后端的契约级断言**。

### P1-3｜后端链不共享超时预算：最坏 375s > 客户端 240s 【P1 · 静态确认】

- **证据**：`BackendRouter.solve` 把**完整** `timeout` 原样传给每个后端（`backends.py:264-292`）。
  默认上限分别为：`--cfsolve-timeout 120`（`service.py:1566`，且 `cfsolve_backend.py:110` 实取 `min(120, timeout+30)`）、
  `--pydoll-wait 45`、`MAX_TIMEOUT 120`（`service.py:112`）、FlareSolverr `request_timeout 90`（`backends.py:94`）
  ⇒ 四后端全配时最坏 ≈ **375s**，而 Go 客户端 `hc.Timeout = 240s`（`cfsolve.go:236`，注释写着"覆盖服务端最坏 155s"）。
- **影响**：四后端全配时，客户端先超时，拿到裸网络错误而不是结构化 `*APIError`，错误码体系失效；
  且单个用户请求可能占住 worker 6 分钟。
- **修法**：**T-35**——`Deadline` 对象贯穿全链（入口算一次总预算，每棒 `min(剩余, 单棒上限)`，剩余 ≤0 立刻终止）。

### P1-4｜并发冷域打穿求解（T-09，v3.0 遗留） 【P1 · 静态确认】

- **证据**：`cfsolve.go:277-298` `Get` 无 per-host 合并；50 goroutine 打同一冷域 → 50 次 `/solve`（服务端有 inflight=8 闸门，但那是拒绝而非合并）。
- **影响**：多进程 + 共享缓存已缓解；单进程内多协程仍制造 N 倍浏览器占用与 429。
- **修法**：**T-09**（零依赖 per-host singleflight，约 40 行 + 4 个用例）。

### P1-5｜没有按 host 限流，`RATE_LIMITED` 是死错误码 【P1 · 已验证】

- **证据**：`ErrorCode.RATE_LIMITED` 全仓 4 处引用（`errors.py:25,49`、`backends.py:242`、`tests/test_backends.py:271`），
  **无任何 raise 点**；`docs/API.md:129` 也诚实写了"预留，默认未启用"。
- **影响**：一个客户端死循环就能把同一目标站打到"IP 提分"，烧掉的是**整个部署的出口信誉**（本仓库最贵的资源）。
  这是唯一"防不住外部、但能防住自己"的保护。
- **修法**：**T-31 的一部分**——per-host token bucket（默认每域 6 次/分钟，`--host-rate` 可调），超限返回 `429 rate-limited`。

### P1-6｜`/detect` 无准入 + 重定向不复检（第二处 SSRF） 【P1 · 已验证+静态确认】

- **证据**：
  - 无准入：`_run_detect`（`service.py:1476-1491`）直接 `probe_protection(url)`，**不取任何信号量**；
    `ThreadingHTTPServer` 线程无上限 ⇒ 并发 `/detect` = 线程数 × 15s 出站，无背压放大器。
  - 重定向：`probe_protection` 用 `urllib.request.urlopen`（`service.py:195`），该 API **默认自动跟随最多 10 跳且不回调守卫**。
    `_run_detect` 只对**入口 host** 调一次 `_check_target`。
    本轮实测 V11：`GET /detect?url=http://github.com/`（301→https）返回 `status=200` ⇒ 跟随确实发生。
- **影响**：`detect.summarize` 不回传 body（只回状态码/命中签名/cookie 名），所以不是任意文件读取，
  而是**任意主机可达 + 状态码/特征回显** ⇒ 可做内网端口与服务探测、云元数据端点存在性判定。需 token，属"已认证越权"。
- **修法**：**T-31**——关闭 urllib 自动跟随，逐跳 `guard_hop()`（含非 http(s) 协议直接拒），decoupled 独立信号量 `--max-detect`（默认 4）。

### P1-7｜Go 池把终止性错误记成节点故障；探活看不见 `503` 【P1 · 静态确认】

- **证据**：
  - `pool.go:274` 对**任意** `err` 调 `node.markFail(...)`，包括 `400 invalid-request` / `401 unauthorized` / `429 busy`。
    连续 2 次 ⇒ 健康节点被摘除 30s（`pool.go:104-112`、`:148`）。服务端早已有 `TERMINAL_CODES`（`backends.py:237-244`），**Go 侧无对应物**。
  - `pool.go:311-330` `healthLoop`：`err==nil && ready` → `markOK`；`err != nil` → `markFail`；
    **`err==nil && ready==false` 什么都不做**——而这正是"浏览器死了"在服务端的表现（`503` + 合法 JSON，`service.py:1192-1237`）。
  - `pool.go:291-305` `Do` 在回放 403 时仍 `markOK`（因为 `DoWith` 无状态码判据）。
- **影响**：429 高发时池子会自我雪崩（好节点被摘）；浏览器挂了的节点在池视图里永远健康。
- **修法**：**T-10 同批**——把 `TERMINAL_CODES` 语义搬到 Go（`APIError.Code` 白名单不 markFail），探活补 `!ready` 分支。

### P1-8｜无 CI：174 + 17 项测试没有回归保护 【P1 · 已验证】

- **证据**：仓库根无 `.github/`。
- **影响**：本轮已经能观察到后果——**同一代代码里，FlareSolverr 后端守住的 TTL 不变量在 cfsolve/pydoll 上失守**（P1-2），
  没有任何自动机制能发现"新后端没继承契约"。
- **修法**：**T-39**（三 job 全离线：py 3.11/3.14、go vet+test -race、node --check）。

### P1-9｜覆盖率 69% < 项目 80% 门槛；`service.py` 仅 55% 【已验证】

- **证据**：V3。重灾区：`service.py` 55%（缺 `_do_solve` 主体、`_collect_token`、`_install_request_guard` 的多分支）、
  `pydoll_backend.py` 40%、`engines.py` 57%。
- **影响**：这三块恰好是"最脏、最容易回归"的部分；`_install_request_guard` 的三态解耦（顶层拦截=整次失败 / 子资源拦截=只 abort）没有测试兜住。
- **修法**：**T-39 的一部分**——CI 里跑 `--cov`，`--cov-fail-under=80`；先补 `_install_request_guard` 与 `_do_solve` 的关键分支（预计 +12 个用例）。

### P2-1｜代理池只覆盖求解侧，回放侧没有出口绑定 【P2 · 静态确认】

- **证据**：服务端有完整 `ProxyPool`（`proxypool.py`，`--proxy`/`--proxy-egress-ip`），
  但 `gocfsolve` 全模块**没有任何代理 Option**，只有 `cfsolve.go:257` 的 `Proxy: http.ProxyFromEnvironment`。
  另外 `cfsolve_backend.py:154` / `pydoll_backend.py:201` 把 `egress_id` 硬编码成 `"cfsolve"`/`"pydoll"`，
  **完全绕过代理池**（它们在自己的进程里直连）。
- **影响**：多出口部署下，浏览器经出口 A 求解、Go 回放走环境代理或直连（出口 B）⇒ 静默 403。
  单出口场景碰巧可用，所以至今没暴露。
- **修法**：**T-38 相邻**——Go 侧加 `WithProxy(func(egressID string) (*url.URL, error))`，
  按 `Clearance.EgressID` 选 Transport；两个硬编码 `egress_id` 改为透传 `Solver` 的出口标识。

### P2-2｜`service.py` 1704 行、4 类职责混杂 【P2 · 静态确认】

## 7. 核心新能力：`route=auto` 自动路由闭环（T-32/T-33/T-35）

### 7.1 现状：能力已建，闭环未合

`POST /detect` 已经能给出 `recommendation.route`（7 种取值）；`POST /solve` 有 4 个后端。
**两者之间没有数据流**：调用方必须自己调两次，自己写 if。结果：

- 无盾站（`direct`）也被送进浏览器浪费 16–20s 与 1.2GB；
- 明确不支持的站（DataDome/Akamai）也被盲目求解，失败后返回 `unsolved`，调用方无法区分"我们不会"与"这次没解出来"；
- 纯协议站（`pure_protocol_may_work`）没有优先走纯协议，白付浏览器成本。

### 7.2 目标契约（向后兼容，默认行为不变）

```http
POST /solve
{
  "url": "https://target/",
  "timeout": 45,
  "want": "clearance",
  "route": "auto"            // 新增可选：auto | direct | pure | browser | fixed（缺省=fixed=今天的行为）
}
```

成功后**新增**字段（老客户端忽略即可）：

```json
{
  "ok": true, "solved": true, "cf_clearance": "...",
  "routed_by": {
    "mode": "auto",
    "detect": {"protected": true, "providers": ["cloudflare"], "challenge_type": "managed",
                "route": "browser", "confidence": 1.0, "cached": false, "probe_ms": 420},
    "chosen_backend": "camoufox",
    "escalations": [{"from":"cfsolve","reason":"profile-expired","next":"camoufox"}]
  }
}
```

### 7.3 决策表（`solver/route.py`，纯函数，可离线单测）

| detect 结论 | 首选后端 | 说明 | 失败升级 |
|---|---|---|---|
| 未命中任何特征（`protected=false`） | **不求解，直接回放** | `solved=false, error_code="no-challenge"`？→ **不**：返回 `ok=true, solved=true, route="direct", cookies=[]`，让业务直连 | 业务拿到 403 则回到 `browser` |
| `cloudflare` + `managed/jsd/interactive/embedded` | cfsolve（若配置）→ camoufox | 纯协议 18.4s 零浏览器；失败立刻降级 | `profile-expired`/`rejected` → camoufox |
| `cloudflare` + `turnstile`/`recaptcha_v3` | camoufox（`want` 已指定） | 一次性 token 必须浏览器内取 | 不降级（换后端无意义） |
| `cloudflare` + `aws_waf` | camoufox | pydoll 备选 | pydoll |
| **其他厂商**（DataDome/Akamai/PerimeterX/…） | **拒绝求解**，返 `error_code="unsupported-provider"` + `hint` | 不要假装能解——诚实比白等 45s 有价值 | 无 |
| `direct_unless_blocked` | 直连探测；403 再 `browser` | 省一次浏览器 | `browser` |

### 7.4 失败原因分类（T-33，`RouteReason` 枚举）

| 原因码 | 判据（有证据的） | 升级动作 |
|---|---|---|
| `no-challenge` | cfsolve stderr 含 `not challenged`（`cfsolve_backend.py:174`） | **不重试**，直接判 `route=direct` |
| `profile-expired` | stderr 含 `rejected`（`:179`） | 换浏览器后端，并**告警**"profile 该重录了" |
| `ip-blocked` | stderr 含 `blocked`（`:177`） | **不换后端**（换后端没用），若配代理池则换出口，否则直接返错 |
| `challenge-unsolvable` | 到预算上限仍无 cookie | 换后端一次，仍失败则返 `unsolved` + 站点名 |
| `navigation-error` | `goto_error` 非空（`service.py:1095`） | 判 `transport(502)`，**切换后端前先确认网络** |
| `too-slow` | 单棒耗时 > 该后端历史 P90×1.5 | 换后端（这是唯一"性能型"升级） |

> **纪律**：升级阶梯**最多 2 跳**（`cfsolve → camoufox → flaresolverr`），禁止全链轮询；每次升级必须把原因写进 `escalations[]`，
> 便于事后统计"哪一棒最常失败"。**任何 `ip-blocked` 都不得继续换后端重试**（这是烧 IP 的典型姿势）。

## 8. 缓存层：FileStore → SQLite(WAL)（T-36，D-2）

### 8.1 为什么换（现状的真实成本）

| 现状（`solver/cache.py` 298 行） | 问题 |
|---|---|
| 每键一个文件（默认上限 4096） | 多进程共享目录时，`max_files` 淘汰按 **mtime 最旧**，跨进程语义模糊；进程 A 可能删掉进程 B 刚写的热条目 |
| `purge_expired()` 扫目录 | 每次 O(n) 文件 stat；n=4096 时单次 purge 数百 ms，且要遍历所有 `*.bin` 再把 `salt.bin` 排除掉（历史上踩过"盐被当缓存删掉"的坑，`plans/状态/...md` 有记录） |
| 无索引 | 拿不到"每域求解次数/失败率/平均耗时"，而这正是 W3 想要的运维数据 |
| 原子性靠临时文件+rename | 单文件是对的；但**跨文件的批量淘汰**没有事务，崩溃可能留下孤儿文件 |

### 8.2 目标设计

```sql
-- 单文件：<cache-dir>/cache.sqlite3（WAL 模式）
CREATE TABLE IF NOT EXISTS entries (
  key         TEXT PRIMARY KEY,        -- sha256(host|egress)[:32]
  host        TEXT NOT NULL,           -- 新增：便于按域统计/清理
  egress      TEXT NOT NULL,
  value       BLOB NOT NULL,           -- Fernet 加密后的 JSON
  expires_at  REAL NOT NULL,
  created_at  REAL NOT NULL,
  backend     TEXT NOT NULL DEFAULT '' -- 新增：哪个后端产出
);
CREATE INDEX IF NOT EXISTS idx_expires ON entries(expires_at);
CREATE INDEX IF NOT EXISTS idx_host    ON entries(host);

-- 统计表（不放凭证，只放计数）
CREATE TABLE IF NOT EXISTS host_stats (
  host TEXT PRIMARY KEY,
  solves INTEGER NOT NULL DEFAULT 0,
  failures INTEGER NOT NULL DEFAULT 0,
  sum_elapsed REAL NOT NULL DEFAULT 0
);
```

**关键点（每条对应一个已知坑）**：

| 点 | 做法 | 为什么 |
|---|---|---|
| 并发 | `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA busy_timeout=5000;` | 多进程共享目录的唯一正确姿势；WAL 允许并发读单写 |
| 加密 | 沿用现有 `Fernet + PBKDF2` 派生（`cache.py` 已有），**加密在应用层、存 BLOB** | 不把加密推给 SQLite（无内置 AES）；保持"磁盘无明文凭证"这条不变量 |
| 盐 | 仍落 `<cache-dir>/salt.bin`，**不放进库里、不进淘汰** | 历史上"盐被当缓存删掉导致全部解不开"的坑 |
| 淘汰 | `DELETE FROM entries WHERE expires_at < ?` + 超限时 `DELETE ... ORDER BY expires_at LIMIT ?` | 用索引，O(log n)；按**过期时间**而不是 mtime，语义与"凭证寿命"一致 |
| 崩溃 | 每次 `set` 单事务；不做跨键批量写 | 事务内要么全成要么全败 |
| 降级链 | `--cache-backend auto|sqlite|file|memory`，`auto` = sqlite 可用则 sqlite，否则 file，再否则 memory（**降级必须打日志 + 写进 `/health.cache_backend`**） | 不能因为磁盘/权限问题让服务起不来 |
| 兼容 | 迁移：首次启动若发现同目录有旧 `*.bin` 文件，**不迁移**（凭证很短命，重建即 1 次求解），直接清空并留一条日志 | 避免写一次性迁移代码 + 一次性 bug |

### 8.3 接口不变（只换实现）

```python
class Store(Protocol):
    def get(self, key: str) -> dict | None: ...
    def set(self, key: str, value: dict) -> None: ...
    def purge_expired(self) -> int: ...
    def __len__(self) -> int: ...
    def stats(self) -> dict: ...   # 新增：给 /metrics 用
```

`build_store(cache_dir, token, max_files, backend="auto")` 签名只加一个可选参数 ⇒ 所有调用点零改动。

### 8.4 验收（G2）

- 同一套 `tests/test_cache.py` **参数化跑两遍**（`@pytest.mark.parametrize("backend", ["file","sqlite"])`），断言完全一致；
- 多进程 A/B：4 进程写读 10 分钟，断言"同域只有 1 次求解"（复用 T-40 的 loadtest，mock 后端）；
- 跨进程可见性：进程 A `set` → 进程 B `get` 命中（今天靠文件也能做到，属于回归保护）。

### 8.5 风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| WAL 在 Windows 网络盘/NTFS + 多进程下 `database is locked` | 中 | 高 | `busy_timeout=5000` + 失败降级到 FileStore（一次重试后） |
| 单文件成为 I/O 热点 | 低 | 中 | 缓存条目只有几百条量级（域数 × 出口数），不是热点 |
| 加密 BLOB + 索引导致库膨胀 | 低 | 低 | 每条 ~500B，4096 条 ≈ 2MB |

## 10. 安全加固清单（T-28/T-31 的验收面）

| 项 | 现状 | 目标 | 判定 |
|---|---|---|---|
| SSRF 入口统一 | ❌ router 路径绕过（P0-1） | 守卫在 handler 入口执行一次，与后端无关 | F5：参数化 4 种后端组合，内网 URL 一律 `invalid-request` |
| 重定向逐跳复检 | ❌ `/detect` 不查（P1-6） | `guard_hop()` 逐跳 + 非 http(s) 拒绝 | 本地双跳实验：入口公网 → 302 内网 → 必须被拒 |
| 出站协议白名单 | ⚠️ | 只允许 `http/https`（urllib 的 opener 装了 `file:`/`ftp:` handler） | 单测：`file:///etc/passwd` 必拒 |
| 准入（`/detect`） | ❌ 无 | 独立信号量 + 满即 429 | 单测：并发 5 > `--max-detect 4` → 第 5 个 429 |
| per-host 限流 | ❌ 无（`RATE_LIMITED` 死码） | token bucket（默认 6/min/域） | 单测：7 连发 → 第 7 个 `429 rate-limited` |
| token | ✅ Bearer + `compare_digest` + 首启生成 0600 | 增加**多 token 轮换**（`--token-file` 支持多行）便于不停机换 key | 单测：旧 token 在新 token 生效后仍有 5 分钟宽限 |
| 日志凭证 | ✅ 只打长度/指纹（`token_fingerprint`） | 审计日志只记 `host/backend/result/ms`，**绝不记 cookie 值** | `grep -c cf_clearance logs/*.jsonl` == 0 |
| chunked 请求体 | ⚠️ 不解析且不关连接 | 显式拒绝 `Transfer-Encoding: chunked` 并 `close_connection=True`（否则未读字节会被当下一请求） | 单测：带 chunked 头的请求 → 400 + 连接关闭 |
| Windows 权限 | ✅ `chmod 0600` 在 NTFS 无效已写入 `docs/API.md` | 文档保持诚实，不假装"已加固" | 文档复核 |

## 15. 实验卫生（D-4：60 次真机预算）

**总预算 60 次**，分三批，**不跨批挪用**。所有批次共用同一份纪律条款。

| 批次 | 用途 | 次数 | 闸门（没有满足就不许开始） |
|---|---|---|---|
| **A** | **同站双臂**：persona 固定 vs 随机（3 站 × 2 臂 × 5 次） | 30 | 先跑 `--dry-run`；同一站两臂间隔 ≥30s；**必须同站**（不许再出现 v3.0 那种站点间对照） |
| **B** | 路由收益（G1）：`route=auto` 在 3 类站（无盾/CF managed/不支持厂商）各 2 次 | 10 | 必须先有 A 批结论（否则无法归因） |
| **C** | geoip A/B（2 站 × on/off × 3 次） | 12 | 先查 camoufox 官方文档确认 `geoip=True` 是否引入外部 MMDB 请求；**有外部请求直接否决** |
| 预留 | 手工排查 | 8 | — |

**硬性规则（逐条强制）**：

1. 只发 `GET` 目标站首页；不登入、不提交、不并发打同一站；
2. 同站串行、间隔 ≥30s；
3. 每站先打一次无 cookie 基线；
4. **累计失败 ≥5 次 → 立即停止全部实验**，写"IP 可能已被提分"，隔 24h 再评估，**不许换 IP 立刻重试**；
5. 每次请求落 `plans/证据/exp-<日期>-<批次>.log`；`cf_clearance` 只写长度，不写值；
6. 实验脚本必须支持 `--dry-run`；
7. CI 永不执行真实联网实验；
8. **单次实验结论必须同站可比**，不同站数据只做定性描述。
