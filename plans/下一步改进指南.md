## 0. 本版速览（先读这一页）

### 0.1 一句话结论

**v5.0.x 已经把「服务面」做扎实了**（328 用例全绿 / 82% 覆盖率 / 33 处 findings / 4 条后端回落链 / 多进程池 / 容器实测）；
**但「研究面」目前是零资产**：CF 一改版，纯协议路线的全部知识必须从零再挣一遍。原因是三个断点（全部有本轮证据）：

| # | 断点 | 本轮证据 | 后果 |
|---|---|---|---|

| **2** | **结构断言只活在文档里，不在测试里** | 证据 JSON 里写着「stage2 有 6+ 硬性结构断言（dispatcher / collection fn / probe state / counter / token / input）」，但 `tests/` 中**无一条**对应断言（`静态确认`：`grep -i "stage2\|counter field" tests/` 空） | CF 改版后只能靠"跑一次真机看报错"来定位，无法离线知道"是哪条断言坏了" |
| **3** | **补丁靠人肉推，没有回归门禁** | `tools/cfsolve-patches/*.patch` 共 393 行、2 份补丁，`README.md` 自述「本补丁把从 0 到能跑打通 2/3」；没有任何脚本能在改补丁前后给出**差分结论**（`静态确认`） | 补丁一多就无法判断"这次修好的是 net 收益还是 net 亏损"；上游一跟进就冲突 |

**v6.0 的真正交付物不是新功能，而是这句话的实现**：
> **下一次 CF 改版时，我们能在一小时内指认出「哪一条结构断言坏了、坏在哪一行 AST」，并且这次知道要留下什么样本。**

## 2. 第一性原理：为什么「研究」必须工程化

### 2.1 剥到最底层，这个项目在赌什么

我们的求解器**不是**"算出一个算法答案"，而是一组**关于 CF 挑战程序结构的假设**：

```
假设 A：挑战页里某处有 inline JS，且含 _cf_chl_opt          → source.rs::inline_javascript
假设 B：`setRequestHeader('cf-chl', "...")` 里的 token 是静态串 → source.rs:280-297
假设 C：初始 VM 程序里的 encoder / alphabet / modulus 可用固定形态读出 → program.rs:169-193
假设 D：stage2 的响应程序里有 6 类固定结构（dispatcher / collection fn / probe state / counter / token / input）→ stage2/analysis/*
```

**这些假设全部会被 CF 改版打破，且打破方式每次不同**（2026-11-03 那次是「computed-property 字符串别名 + 运行时字段名解码」）。

于是问题变成：**当假设被打破时，我们如何以最短路径知道"哪条假设破了"？**

### 2.2 三个必要且充分的不变量（本版的全部设计依据）

| 不变量 | 现在的状态 | v6.0 的做法 |
|---|---|---|
| **I1 样本可重放**：任何一次"破/通"都要能凭本地文件复现，不需要再联网 | ❌ 0 份（B6） | T-66 快照留存 + T-67 分析台 |
| **I2 断言可执行**：每条假设 = 一条可跑的红/绿断言 | ❌ 只在文档 | T-68 断言矩阵 |
| **I3 差分可比较**：改动前后对同一批样本的输出可 diff，且 diff 可读 | ❌ 无 | T-72 / T-75 |

**代价/收益量化（`合理推断`，基于本轮审计的工作量估算）**：

| 场景 | 现在（无资产） | v6.0 之后（有资产） |
|---|---|---|
| CF 改版，纯协议开始失败 | 起服务 → 真机跑 → 读 500 行 Rust 报错 → 猜是 deobf 还是 stage2 → 手改 → 再真机（**一次循环 ~2-4h，且每次都要真机预算**） | 把新快照塞进 `corpus/` → `research.py diff` 输出"假设 B 的 token 提取 0 命中，假设 D 的 counter 断言失败" → 只改那一处 → 离线跑断言 → **0 真机** |
| 上游 cfsolve 跟进新版 | 手工 `git apply` 试 → 冲突 → 人读 | `research.py patch --check` 报冲突文件与行号；`research.py patch --verify` 跑补丁回归 |

### 2.3 为什么**不能**用"多写点文档"代替

文档回答"上次结论是什么"，测试回答"现在还成立吗"。这两者是**正交**的：
`docs/纯协议-cfsolve.md` §6 的耗时解剖非常准确，但它是**静态结论**——它无法在 CF 换成新 PoW 预算的当天告诉你"这条结论过期了"。
**只有可执行断言有"过期即红"的能力。** 这是本版存在的唯一理由。

### T-71｜计算属性 / 别名规则的「自动推导」（把 11-03 手工放宽的那两行变成规则生成）

- **背景（证据）**：11-03 补丁的核心是两处**手工放宽**：`challenge/expression.rs` 的 Member 求值分支支持"静态可求值的计算属性 key"、`deobfuscate/analysis/properties.rs` 的 `is_static_member_key` 放宽（`tools/cfsolve-patches/cfsolve-newcf-computed-key-20261103.patch`，81 行，`静态确认`）。手工放宽的风险是：**放宽过头 → 把真正动态的属性误判为静态 → 后续分析在错的 AST 上跑，报错位置漂移；放宽不够 → 死锁**。
- **目标**：从样本中**聚类**出"CF 用来做别名的形态"，把规则写成**数据**（一个形态清单），而不是散落在两处 `if` 里；每次新版只需更新清单。
- **改法**：
  1. `tools/cfsolve-patches/analyze/alias_shapes.py`：对 deobf 后的脚本抽取所有**计算属性访问**节点（`obj[expr]`），把 `expr` 归一化成"形态签名"（例：`IDENT`、`MEMBER(IDENT,IDENT)`、`CALL(IDENT,[LIT,EXPR])`、`BINOP(*)`、`FUNC(...)`），统计频次与上下文；
  2. 输出 `alias-shapes.json`：`{形态签名: {次数, 是否可静态求值(用现有求值器实测), 前 3 个例子(file:line)}}` —— **"是否可静态求值"必须实测，不许猜**；
  3. 把 `properties.rs` / `expression.rs` 的白名单改成**读清单**（Rust 侧加一个 embedded 常量或 `include_str!`，保持零运行时依赖），Python 侧生成清单 → 两边用同一份数据；
  4. `research.py aliases <corpus-id>` 输出清单与"当前实现会误判的形态"。
- **验收标准（改前必红）**：
  - `test_alias_shape_normalization_is_stable`（同一表达式不同变量名 → 同一签名）
  - `test_alias_rule_set_matches_rust_side`：Python 生成的清单与 Rust 侧读到的清单**逐项相等**（防两侧漂移；这条是核心）
  - `test_alias_rule_regression_on_synthetic`：构造 `obj[helper.key]`（已知必须判静态）与 `obj[getKey()]`（已知必须判动态）→ 两条都必须正确
  - 有真样本时：`test_alias_shapes_on_corpus_has_no_unknown_static`（断言"被判静态的形态"里没有"实测不可静态求值"的项）——**无样本时 skip with reason**
- **风险**：**L2**（要改 Rust 侧的两处判定逻辑，虽是"数据驱动化"，但触及 11-03 刚打穿的核心路径）。缓解：①先只做 Python 侧清单生成（不接 Rust）并跑通断言；②接 Rust 分独立 commit；③**任何放宽都必须带"反向用例"**（证明没有放宽过头）。
- **回滚**：清单接入层加开关 `CFSOLVE_ALIAS_RULES=off`（环境变量，读不到就用内置旧白名单）；两处 commit 可分别 revert。

### T-72｜stage2 counter 断言「离线收敛」（本版最硬的一块）

- **背景（证据）**：11-03 的卡点原文是 `stage2/analysis/envelope.rs:37 'record counter field not found'`，诊断结论是「CF 新版 probe 程序的 VM 形状变化，属 stage2 深层分析器适配」，且「stage2 有 6+ 硬性结构断言，CF 改版后每一处都可能再变，是长尾跟随工程」（`plans/证据/cfsolve-computed-prop-patch-20261103.json`，`静态确认`）。

- **改法（严格四步，顺序不可颠倒）**：

### T-82｜门禁修正：ResourceWarning 真绿 + 拆分文件局部覆盖率

  1. **ResourceWarning + 间歇红（两件事，别只做一件）**：

### B. Rust 侧改动纪律（T-71/T-72/T-73 涉及 `D:\cfsolve-upstream`）

### C. 执行纪律（沿用历史版并加强）

1. **红灯先行**：每张卡先写"改前必红"用例，看到红再改代码。**没有红灯的卡不许标 Done**（历史教训：F5 从未写出 → T-28/T-29 假 Done 骗了一整轮）

3. **一卡一 commit**；提交前 `git status`/`git diff` 只含本卡范围，无 secrets、无临时文件
4. **证据落盘**：`evidence/<task_id>.json`（服务面）/ `plans/证据/`（研究面）；**先过 `corpus.py redact --check`**
5. **状态只记 `workflow_status.md` §2**，本文件保持"计划"身份
