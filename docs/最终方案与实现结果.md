# 最终方案与实现结果

> 这份文档回答三个问题：**最终走哪条路、为什么、跑出来的真实数据是什么。**
> 所有数字都是本机实际运行输出，命令与结果一一对应。

---

## 一、最终方案（已实现、已端到端跑通）

**路线 B：Camoufox 求解 sidecar + Go 原生 HTTP 回放。**

```
┌──────────────────────┐   POST /solve    ┌────────────────────────────┐
│  Go 网关 / 业务代码   │ ───────────────► │ solver/service.py (:8878)   │
│  gocfsolve.Client    │ ◄─────────────── │  Camoufox（C++ 层指纹篡改） │
└──────────┬───────────┘   cf_clearance   └────────────────────────────┘
           │                + user_agent
           │  net/http + 同 UA + 同 Cookie + 同出口 IP
           ▼
      目标站（200）
```

**为什么不是纯协议/纯算**：见本目录 `Cloudflare过盾方案可行性侦察报告.md` §14–16 ——
jsd 明文码表时代已终结，managed challenge 的编排脚本我们能在 jsdom 与 goja 里执行，
但拿不到 `cf_clearance`（CF 校验的是环境真实性，不是算法）。这是实测结论，不是推断。

**为什么 Go 侧不需要 uTLS**：实测该批站点不严查 JA3（同一 cookie + 同 UA，用
firefox/safari/chrome 三种 TLS 指纹回放**全部 200**），标准库 `net/http` 足够。
uTLS 仅作为遇到严查 JA3 站点时的兜底，非默认依赖。

## 二、实现清单

| 组件 | 文件 | 职责 |
|---|---|---|
| 求解服务 | `solver/service.py` | 持有 Camoufox，`POST /solve` 返回 `cf_clearance` + UA + cookies；按域缓存；`GET /health`、`GET /stats` |
| Go 客户端 | `gocfsolve/cfsolve.go` | 调用求解服务、本地缓存 + 提前续期、`Do()` 自动套 UA/Cookie 回放 |
| 端到端验证 | `gocfsolve/examples/endtoend/main.go` | 一条命令跑通「求解 → 回放 → 校验 200」 |

### 求解服务接口

```http
POST /solve   {"url": "https://target/", "timeout": 45, "force": false}
→ 200 {"ok":true, "cf_clearance":"...", "user_agent":"...", "cookies":{...},
       "expires_in":1500, "expires_at":1761..., "elapsed":18.12, "cached":false}

GET  /health  → {"ok":true,"browser":"camoufox","cached_domains":1,"solves":2,...}
GET  /stats   → 同上（含 cache_hits / avg_elapsed_sec）
```

### Go 客户端关键 API

```go
cli := cfsolve.New("http://127.0.0.1:8878")

cl, err := cli.Get(ctx, target)      // 优先本地缓存 → 服务端缓存 → 真实求解
cl, err := cli.GetFresh(ctx, target) // 强制重新求解

resp, err := cli.Do(ctx, req)        // 自动取 clearance 并套 UA/Cookie 回放
resp, err := cli.DoWith(ctx, req, cl) // 用指定 clearance 回放
```

## 四、部署

```bash
# 1) 一次性准备
pip install camoufox && python -m camoufox fetch

# 2) 起服务（建议每个实例一个进程/端口，横向扩）
python solver/service.py --host 0.0.0.0 --port 8878 --ttl 1500

# 3) 业务侧
cli := cfsolve.New("http://cfsolve:8878")
```

**内存与并发**：单实例约 **700 MB**（Firefox 引擎），单 worker **串行**求解
（Playwright sync API 绑定线程，见「踩坑」）。要提升吞吐就多起实例 + 前面挂轮询/一致性哈希，
不要把并发压在一个实例上。

## 五、踩过的两个真 bug（都已修）

### 5.1 Playwright 同步 API 绑定线程 → 多线程服务必崩

现象：第一个请求成功，第二个请求报
`cannot switch to a different thread (which happens to have exited)`。

原因：`ThreadingHTTPServer` 每个请求一个新线程，而 Camoufox/Playwright 的 sync 对象
**只能在创建它的线程里使用**。

修法：服务改为「单 worker 线程持有浏览器 + 队列派发」，HTTP 线程只做收发。

### 5.2 `force=true` 把服务端缓存打穿

现象：第二次请求仍然耗时 14s，`cached=false`。

原因：Go 客户端的 `Get()` 复用了 `GetFresh()` 的 `force=true`，导致服务端每次都重新求解。

修法：拆出内部 `solve(ctx, target, force)`；`Get` 传 `false`（允许服务端缓存），
`GetFresh` 传 `true`。修完后跨进程命中缓存 **0.00s**。

### 5.3 另一个已修的细节

客户端命中**本地**缓存时，返回的副本要标记 `Cached=true`，否则调用方无法区分
"又启动了一次浏览器"和"直接用的缓存"。

## 六、已知限制（诚实披露）

1. **单实例 700 MB 内存 + 串行求解**，吞吐 ≈ 1 次 / 15s。要 1 QPS 需 ~15 个实例
   （可共享进程但需独立 worker 线程/进程）。
2. **cf_clearance 绑 IP**：求解与回放必须走**同一个出口 IP**。要走代理池，得把 proxy
   传给求解服务，并保证回放时用同一出口。
3. **约 30 分钟时效**，缓存 TTL 默认 1500s 并提前 5 分钟续期。目标站改 CF 策略可能要调。
4. **按域隔离**：一个 clearance 只对一个 zone 有效，缓存按 host 键。
5. **CF 改版风险**：Camoufox 依赖 C++ 层补丁，CF 若上新的指纹面（如更严的 WebGL/Audio 交叉校验），
   需要跟随 Camoufox 上游升级。这是选这条路的长期成本。
6. **状态更新（v2.0）**：以下四项已从"未做"变为"已实现并有测试"——
   ①代理池（`solver/proxypool.py`：按域一致性哈希粘性 + 评分 + 冷却退避，凭据不进日志/`/health`）；
   ②落盘共享缓存（`solver/cache.py`：Fernet 加密 + 原子写 + 过期清理 + 上限淘汰，跨进程共享）；
   ③多后端接缝（`solver/backends.py`：`BackendId` 白名单 + 有序路由 + `attempts` 轨迹，
   已接一个自托管 FlareSolverr 兼容后端作兜底）；
   ④可观测性（`/metrics` Prometheus + `/health` 三态语义）。
   **仍未做**：多实例的统一调度器（当前靠"一进程一端口 + 外部轮询/一致性哈希"）、告警接入、
   跨机共享存储（v3 议题）。
   ⚠️ 兜底后端（FlareSolverr）只做了契约级验证，**未对真实自托管实例做真机复测**；
   且该上游已进入维护模式，不要把它当主力。

## 七、什么时候不要用这条方案

按成本从低到高，先试前面三档：

1. **换入口**：有没有不带盾的域名 / App API / 上游直连？（我们过去多个逆向项目都是这样省掉的）
2. **用镜像副本**：内容类需求可用 archive / reader 视图，完全不解盾。
3. **复用已有 cookie**：如果人工过一次盾即可，直接把 cookie + UA 存下来给 Go 回放（本仓库
   `gocfsolve/` 就是这个用途，零额外依赖）。
4. 以上都不行，再上本方案的 Camoufox 求解服务。
