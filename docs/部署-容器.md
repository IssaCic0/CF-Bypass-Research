# 部署：容器与多 worker

> 面向"要跑起来"的人。项目**没有生产环境清单**（无服务器/云凭证），所以这里给的是
> 可复现的部署方式 + 回滚方式，而不是"我们的线上部署步骤"。

---

## 1. 三种部署形态（按吞吐选）

| 形态 | 适用 | 命令 | 吞吐 |
|---|---|---|---|
| 单进程前台 | 联调、单域保活 | `.\run.ps1 start` | 串行，≈1 次求解/20s |
| 多进程 + 共享缓存 | **默认推荐**（单机扩容） | `scripts/run-pool.ps1 -Count 4 -CacheDir <dir>` | ≈N 倍（N=进程数） |
| 容器（compose） | 需要隔离/可编排 | `docker compose up -d` | ≈N 倍（3 worker） |

**为什么必须多进程而不是多线程**：Camoufox/Playwright 的 sync API **绑定创建它的线程**，
一个进程里只能有一个 worker 线程在求解。想加吞吐只能加进程。

**为什么多进程必须共享缓存目录**：不同进程各解一次同一个域 = 扩容等于白扩。
所有 worker 必须共用 `--cache-dir` 与同一个 token（token 相同 → 派生同一把加密密钥）。

## 2. 多进程（Windows/Linux 通用）

```powershell
# 4 个 worker（端口 8878..8881），共用缓存目录与同一个 token
pwsh scripts/run-pool.ps1 -Count 4 -CacheDir "$env:LOCALAPPDATA\cfsolve\cache"

# 可选：保活（把"贵操作"挪出请求路径）
pwsh scripts/run-pool.ps1 -Count 4 -Prewarm "steamdb.info,glassdoor.co.uk" -RenewBefore 300
```

启动后自检：

```powershell
.\run.ps1 doctor -Port 8878          # 环境 + 真起一次服务
curl http://127.0.0.1:8878/health    # 期望 state=ready
# 关键：各 worker 的 cache_backend 必须**完全一致**
curl http://127.0.0.1:8879/health | Select-String cache_backend
```

Go 侧用 `cfsolve.NewPool` 接（按域一致性哈希 + 失败摘除 + 冷却回归）：

```go
pool, _ := cfsolve.NewPool(
    []string{"http://127.0.0.1:8878", "http://127.0.0.1:8879"},
    cfsolve.WithPoolToken(token),
    cfsolve.WithPoolMaxFailures(2),
    cfsolve.WithPoolDownDuration(30*time.Second),
    cfsolve.WithPoolHealthProbe(30*time.Second),   // 能发现 503+ready:false
)
defer pool.Close()
```

## 3. 容器

```bash
docker compose up -d --build       # 3 worker，共用 solver-data 卷
docker compose ps                  # 看健康状态
docker compose logs -f solver-1
```

### 镜像体积与"瘦身"（v4.5 实测）

| 构建 | 体积 | 说明 |
|---|---|---|
| 默认 | **4.63 GB** | 保真优先：保留 Camoufox 自带的 **2.1 GB 字体包**（字体枚举指纹的真实性依赖它） |
| `--build-arg SLIM_FONTS=1` | **3.27 GB** | 只删 CJK 字体包（`fonts/M`，810 MB）；已验活：10 s 就绪、`/detect` 200 |
| `--build-arg SLIM_FONTS=2` | 更小 | 删全部字体，**指纹真实性损失更大**，未实测 |

两个坑（写进 Dockerfile 注释了）：
1. **删除必须与 `camoufox fetch` 在同一个 `RUN`**，否则只是加 whiteout，镜像一点不小；
2. **BuildKit 缓存可能给你一个没有浏览器的镜像**（体积好看、一跑就 `CamoufoxNotInstalled`）
   ⇒ 瘦身**必须验活**：`du` + `installed_verstr()` + 起容器打 `/health`。

### `docker compose up -d`（3 worker，v4.5 实测）

`20 s` 三个 worker 全部 healthy；三者 `cache_backend` 与 `ua_fingerprint` 完全一致（共享卷+同一 token）；
内存合计 **2.26 GB**；跨容器 `try_claim` 实测 1 真 2 假、释放后可再抢
⇒ "多 worker 同时抢同一新域只解一次"在真实多容器下成立。

✅ **状态（v4.4/v4.5 已实测）**：`docker build` 成功（1.61 GB），容器**5 秒就绪**，
`/health` `/detect`（真出站）SSRF 守卫 401 `/solve route=auto` `/shutdown` 全部验过；
`/shutdown` 后 `exit=0` 且日志 `优雅退出：在途请求已全部完成`。
完整记录见 `evidence/v44-container.md`。

两个**只有真跑容器才会暴露**的坑（已修，写在这里防止回退）：
1. `camoufox fetch` 必须落在**运行期用户的 HOME**（`ENV HOME=/home/solver` → fetch → `chown` → `USER solver`）。
   落在 root 的 HOME 时，每个新容器首次启动都会重下载浏览器（实测白等 **110s → 修后 5s**）。
2. 端口映射下客户端地址是 **docker 网关**（实测 `172.17.0.1`），所以 `/shutdown` 必须配
   `--allow-remote-shutdown`（compose 里已加；Bearer token 仍是第一道门）。

镜像里的两个刻意设计：

1. **`python -m camoufox fetch` 在 build 阶段执行** —— 放到运行期会导致"镜像能起、一求就挂"
   （首次求解时联网下载几百 MB，直接超时）；
2. **非 root 用户运行** —— 会拉起浏览器进程，root 身份放大一切提权面。

## 4. 热更新（本地语义）

本项目没有生产环境，这里的"热更新"指**本机多进程滚动重启**：

**为什么不能直接 `taskkill /F`**：Windows 上强杀会砍掉正在求解的请求
（实测客户端拿到 `WinError 10054 连接被强制关闭`）。所以走 `/shutdown`：
停收新连接 → 等在途请求（≤10s）→ 再退出。

```bash
# 1) 记录当前版本与配置
git rev-parse HEAD; grep -c . .env

# 2) 逐个重启 worker（不要同时停，否则会全站 503）
for p in 8878 8879 8880 8881; do
  .\run.ps1 stop -Port $p        # 内部先 POST /shutdown，15s 未退才强杀
  .\run.ps1 start -Port $p &
  curl -fsS http://127.0.0.1:$p/health || { echo "起不来，回滚"; break; }
done

# 3) 更新后冒烟
.\run.ps1 smoke -Port 8878
```

**回滚**：`git checkout <上一版本 tag>` 后按上面同一流程重启；缓存无需清理
（换 token 才会作废旧缓存；代码回滚不影响已加密的条目结构，SQLite 与 FileStore 可并存）。

## 4.5 多出口部署：求解与回放必须同一个出口（否则静默 403）

`cf_clearance` 绑 **出口 IP + UA**。服务端 `--proxy` 决定"求解从哪出去"，
而**回放是调用方（Go 客户端）自己发的请求** —— 两边不对齐就会稳定 403，
且现象极像"CF 又改版了"，是最难归因的一类故障。

端到端配方（三段必须对齐）：

```bash
# ① 服务端：配代理池。注意 --egress-id 用于"整机出口"场景；
#    配了 --proxy 时，凭证里的 egress_id 是池自动生成的不含凭据的标识（形如 px:529c4adb33a1）
python solver/service.py --port 8878 --cache-dir /data/cache     --proxy http://user:pass@proxy-a:8080     --proxy http://user:pass@proxy-b:8080

# ② 求解响应里会带 egress_id —— 它是"这份凭证绑在哪个出口上"的唯一凭据
curl -s -H "Authorization: Bearer $TOKEN" -X POST localhost:8878/solve      -d '{"url":"https://target/"}' | jq '.egress_id'

# ③ 客户端：把这个 egress_id 映射到**同一个**代理
```

```go
c := cfsolve.New("http://127.0.0.1:8878",
    cfsolve.WithToken(token),
    cfsolve.WithEgressProxy("px:529c4adb33a1", "http://user:pass@proxy-a:8080"),
    cfsolve.WithEgressProxy("px:7b3e1f0c4d92", "http://user:pass@proxy-b:8080"),
)
// 回放时会按 clearance.EgressID 自动选对应代理；
// 拿到没登记的 egress_id 会 fail closed（ErrNoEgressProxy），而不是"悄悄直连试试"。
```

**纪律**：一旦登记了任何出口代理，回放就 **fail closed**。
原因：直连"试试看"的结果是静默 403 —— 比直接报错难查一百倍。

已验证（`gocfsolve/egress_test.go`，4 个用例）：
`TestReplayGoesThroughTheMatchingEgressProxy`（请求**确实经过**登记的代理）、
`TestReplayFailsClosedWhenEgressHasNoRegisteredProxy`（未登记 → ErrNoEgressProxy）、
`TestNoRegisteredProxyKeepsDirectReplay`（一个都没登记 → 保持直连）、`TestEgressIDSeparatesCache`。

## 5. 常见故障对照

| 现象 | 原因 | 处理 |
|---|---|---|
| `/health` 一直 `starting` | camoufox 二进制没 fetch | `python -m camoufox fetch` |
| `/health` `degraded` + `browser-unavailable` | 浏览器进程崩了 | 自动指数退避重拉；持续出现看 `last_error` |
| 端口起不来（Windows） | 端口被占 或 SO_REUSEADDR 串台 | `netstat -ano \| findstr :8878` 找到并停掉 |
| 多 worker 各解一次 | `--cache-dir` 没指向同一目录，或 token 不同 | 两者必须一致 |
| 401 | 没带 `Authorization: Bearer` | token 在 `./.env`（首启生成） |
| 回放稳定 403 | 凭证失效（换出口/TTL/CF 作废） | Go 客户端会自愈重解（`WithRevalidate`）；服务端看 `routed_by` |
