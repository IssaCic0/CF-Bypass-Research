# 三个参考仓库的深度调研

> 调研方式：浅克隆到临时目录只读，读 README + 入口源码 + 配置/契约，**未运行、未安装**（除已注明）。
> 三个仓库都很新（最后提交 2026-10-29 ~ 10-31）。

## 一、`chris124567/cfsolve` —— 真·纯协议（本仓库已接线）

| 项 | 事实 |
|---|---|
| 形态 | Rust 库 + 两个 bin：`challenge`（求解 CLI）、`capture-proxy`（录制 profile） |
| 规模 | `src/` **47,232 行 Rust**；外加 vendored BoringSSL / wreq / http2 |
| 许可证 | MIT |
| 能力 | 解 **Turnstile widget** 与 **challenge page**，返回 token 或 `cf_clearance`，**不需要浏览器进程** |
| 构建要求 | `rust-toolchain.toml` 钉 Rust 1.98.0 + CMake + C/C++ 编译器 + **libclang** + Git（要打补丁并编译 BoringSSL） |

### 它凭什么能"纯协议"过盾

`src/` 里能看到完整的技术栈：

- `src/vm/interpret/{evaluate,plan,run,builtin}.rs` —— 自带**精简 JS 虚拟机**，能直接跑 CF 的混淆挑战脚本（不需要 V8/SpiderMonkey）
- `src/embedding_page/page.rs`（1123 行）—— 一个**虚拟页面/环境**，回答脚本对 DOM/BOM 的查询
- `src/stage2/call_stack.rs`（2059 行）+ `src/stage2/probes/*` —— 时序、调用栈、时钟探针的伪造
- `src/deobfuscate/*` —— 反混淆（控制流平坦化等）
- `src/http/*` + vendored `btls-sys` —— **TLS impersonation**（冒充 Safari/Chrome 的 ClientHello 与 HTTP/2 帧）
- `profiles/safari-26-ios.json`（17 KB）—— **关键**：`answers`(26) + `challenge_page_answers`(41) 是
  **从真实浏览器录下来的质询应答**；`transport.headers` 里带 UA
  （`iPhone; CPU iPhone OS 18_7 … Version/26.6.2 Mobile/15E148 Safari/604.1`）

**结论**：它不是"算出环境"，而是**用录制的真实环境快照回答质询**，再在本地把挑战密码学算完。
这解释了它的硬约束（README 反复强调）：回放必须**同出口 IP + 同 UA**。

### 对我们的可用性

- ✅ 已作为后端接入：`--cfsolve-bin` + `--cfsolve-profile`，走 CLI 子进程，**零 Python 依赖**；
  解析 stdout（`cf_clearance=...` 或 token），UA 从 profile 的 `transport.headers` 读取，
  错误按它 README 的错误表映射到我们的错误码（NotChallenged/Blocked/Rejected/Network）。
- ❌ **本机无法构建实测**：`libclang` 缺失（BoringSSL 的 bindgen 需要），且构建耗时长。
  这是"缺环境"，不是"方案不行"——构建步骤见 `docs/纯协议-cfsolve.md`。
- ⚠️ profile 是**消耗品**：CF 改版或质询集合变化后要重新录（用它的 `capture-proxy`）。
  这点必须提前告诉用户，否则会以为"接上就一劳永逸"。

## 二、`CloakHQ/CloakBrowser` —— 浏览器内核级指纹改造（本仓库已接线）

| 项 | 事实 |
|---|---|
| 定位 | "Stealth Chromium that passes every bot detection test"，Playwright/Puppeteer **drop-in 替换** |
| 指纹改动位置 | **C++ 源码层 87 处补丁**：canvas / WebGL / audio / fonts / GPU / screen / WebRTC / 网络时序 / 自动化信号 / CDP 输入行为 |
| 附加能力 | `humanize=True`（拟人鼠标/键盘/滚动）；Pro 档宣称 reCAPTCHA v3 得分 0.9 |
| 分发 | `pip install cloakbrowser` / npm，**二进制按需下载**；也有 Docker 镜像 |
| 许可证 | **包装代码 MIT，但编译出来的 Chromium 二进制是专有许可**：最新主版本**需要付费订阅**；另有免费档（旧版本） |

### 与 Camoufox 的关系

同类不同源：
- Camoufox = **Firefox** 的 C++ 层篡改（本仓库默认，实测 96%）
- CloakBrowser = **Chromium** 的 C++ 层篡改（补丁数量更多、还带行为humanize）

两者都能被本仓库当作引擎使用（API 都是 Playwright 兼容），差别在：
Chromium 系对某些站点更"像主流用户"，Firefox 系在 TLS/JA3 上更自洽；
而 Camoufox 免费且可完全离线分发，CloakBrowser 的**二进制不可随本仓库分发**。

### 对我们的可用性

- ✅ 已接为引擎：`--engine cloakbrowser`（内部 `from cloakbrowser import launch`）。
- ❌ **本机未安装**，所以没有真机数据；`--engine cloakbrowser` 会**启动即失败**并打印安装命令。
- ⚠️ 许可证提醒：我们**不能**把它的二进制打进仓库或镜像；用户需自行获取并接受其条款。
  这也是为什么默认引擎仍是 Camoufox。

## 三、`D4Vinci/Scrapling` —— 抓取框架（本仓库不引入，只取机制）

| 项 | 事实 |
|---|---|
| 版本 | 0.5，BSD-3-Clause，Python ≥3.10 |
| 依赖 | `playwright` + **`patchright`** + `browserforge` + `apify-fingerprint-datapoints` + `curl_cffi` + `lxml` … |
| 关键历史 | **v0.3.13 起弃用 Camoufox，改用 patchright**（理由：更快、更省内存、更稳） |
| 能力 | `StealthyFetcher(solve_cloudflare=True)`：自动识别挑战类型并处理 |

### 它最有价值的部分：挑战类型分类 + 交互式点击

`scrapling/engines/_browsers/_base.py::_detect_cloudflare` 把挑战分成
**`non-interactive` / `managed` / `interactive`**（solver 里另有 `embedded`），
`_stealth.py::_cloudflare_solver` 按类型分支：

- `embedded`：定位 `challenges.cloudflare.com` 的 iframe → 等稳定 →
  **点 iframe 内的 `input[type="checkbox"]`**（带 100–200ms 随机延迟）→ 等 networkidle
- `non-interactive`：只等页面自己放行（轮询内容判定），最多 10 轮
- `interactive`/`managed`：先等 spinner 变成 widget iframe，再按
  `#cf_turnstile div, #cf-turnstile div, .turnstile>div>div` 取 bounding box 点击
- 失败按 `__CF_MAX_SOLVE_ATTEMPTS__` 重试

**这正是我们缺的一环**：我们的求解只有"等 cookie"，没有"识别类型 + 必要时点一下"。
对我们的价值不是代码，而是**这份分支策略**（已在 `docs/challenges/managed-challenge.md` 记录为后续可选增强）。

### 对我们的可用性

- ❌ **不引入**：它是抓取框架（`lxml`/`curl_cffi`/`browserforge` 等一大票依赖），
  而我们只需要"浏览器 + 等/点"这一小块；引它等于为了一个函数装一个框架。
- ✅ 可借鉴：挑战类型分类 + 交互式点击策略；以及它 v0.3.13 的迁移决策
  （**弃 Camoufox → patchright**）作为我们"多引擎可切换"的又一佐证。
- ⚠️ 注意：它的 `solve_cloudflare` 在可信度上是"尽力而为"——失败只记日志并把页面原样返回，
  不抛错。我们的语义是**必须明确 success/failure**（`ok/solved`），这点不能照抄。

## 四、横向结论

1. **"纯协议"确实存在，但形态是"录制回放"**（cfsolve），不是"纯算法推导"。
   这与我们早期"A2 goja 跑通但拿不到凭证"的结论不矛盾：goja 是**现场编造**环境，cfsolve 是**重放**环境。
2. **浏览器路线仍是主力**：Camoufox 实测 96%，CloakBrowser 在同一档次甚至更强（但许可受限）。
3. **两条路可以串起来**：纯协议优先（便宜）→ 失败回落浏览器（稳）→ 再回落自托管 FlareSolverr（兜底）。
   本仓库已按这个顺序实现后端路由（`attempts` 会记录每一跳的失败原因）。
4. **没有银弹**：三条路线都受同样的四条硬边界约束（同 IP / 同 UA / 时效 / 按域），
   也都需要应对 CF 改版。差别只在"成本"和"许可"。
